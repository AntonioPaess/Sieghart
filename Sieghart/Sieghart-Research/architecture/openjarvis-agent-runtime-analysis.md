# OpenJarvis — análise do runtime de agentes

**Escopo e evidência:** leitura estática do código oficial de [open-jarvis/OpenJarvis no commit `108d257188cbad85f2e50209d9a61669ea4dec33`](https://github.com/open-jarvis/OpenJarvis/commit/108d257188cbad85f2e50209d9a61669ea4dec33), em 13/10/2026. Nenhum componente OpenJarvis foi instalado ou executado neste Mac. “Verificado” abaixo significa que o caminho existe e tem o comportamento indicado no código desta revisão; não demonstra desempenho ou confiabilidade em produção.

## 1. Mapa de execução real

```text
CLI / SDK / API FastAPI / desktop Tauri
                 │
                 ▼
      SystemBuilder → JarvisSystem
        │ engine + modelo
        │ segurança + ferramentas/MCP + skills
        │ memória + sessões + eventos/traces
        ├──────────────► QueryOrchestrator.ask → inferência direta ou agente
        │                                            └→ loop: modelo → ferramenta → resultado
        ├──────────────► AgentManager (SQLite) ← AgentExecutor ← AgentScheduler
        └──────────────► TaskScheduler (agenda de prompts separada)
```

O ponto de composição é [`SystemBuilder._build`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/builder.py#L142-L369), que cria um [`JarvisSystem`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/core.py) no mesmo runtime Python. [`QueryOrchestrator.ask`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/orchestrator.py#L21-L96) injeta memória quando configurada e escolhe entre chamada direta de engine e agente. A detecção especial de intenção nesse caminho é limitada; não se deve inferir um planejador universal que delega para todos os agentes automaticamente. A [CLI](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/cli/ask.py#L800-L821), o [SDK](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/sdk.py#L271-L336) e o [servidor](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/server/app.py#L153-L316) não têm necessariamente os mesmos defaults e caminhos de execução.

O frontend desktop é Tauri e pode iniciar Ollama e `jarvis serve` como processos auxiliares. Isso confirma uma fronteira de processo no aplicativo distribuível, mas **não** que cada componente do diagrama seja um serviço independente. [Bootstrap e servidor filho](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src-tauri/src/lib.rs#L1482-L1607).

## 3. Fronteiras entre raciocínio, planejamento, ferramenta e interface

**Raciocínio** ocorre em um `InferenceEngine`; **planejamento** pode estar no próprio loop do agente ou em tipo de agente especializado, sem componente universal separado; **ferramentas** passam por um executor e registries; **memória** e **agenda** são auxiliares que o builder conecta; **interação** depende da superfície CLI, HTTP ou desktop. Essa separação é sobretudo de módulos Python e contratos, não de seis serviços independentes. [Engine](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/engine/_stubs.py), [agente](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/agents/orchestrator.py), [builder](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/builder.py).

O catálogo de tipos de agente demonstra estratégias distintas. No caminho gerenciado, [`AgentExecutor.execute_tick`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/agents/executor.py#L186-L350) obtém guarda, escolhe tipo/modelo/ferramentas, registra atividade, executa com retries e finaliza estado/trace. O [`AgentScheduler`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/agents/scheduler.py#L160-L230) consulta vencimentos; threads de execução também podem ser iniciadas por uma rota HTTP específica. Isso não garante que a tarefa continua enquanto o processo está fechado. O gerenciador limpa `running` antigo após reinício, mas precisa decidir novamente o próximo trabalho. [Recuperação de estado](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/agents/manager.py#L164-L190).

## 4. Segurança e recursos que alteram a decisão

O executor possui portas de capacidade, taxa, marcação de dados e confirmação. Contudo, a [configuração padrão](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py) mantém a política de capacidades desativada e `default_deny=false`; perfis endurecidos podem alterá-la. Com servidores MCP externos configurados e sem nomes explícitos, o [`SystemBuilder._resolve_tools`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/builder.py#L464-L533) inclui todas as ferramentas descobertas. Um futuro host Sieghart deve emitir uma lista permitida específica por tarefa e verificar a permissão **em cada chamada**, inclusive após descoberta e retry. A [viabilidade de integração](../integrations/openjarvis-integration-feasibility.md) detalha loopback, TCC, armazenamento e analytics.

**Verificado:** OpenJarvis fornece telemetria/trace local e analytics externo em subsistemas distintos; analytics externo aparece ativado por padrão no [config](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1211-L1230). Não houve captura de tráfego para confirmar transmissões reais. Para o Sieghart, o desenho proposto é métricas técnicas locais sem conteúdo de prompt por padrão, política de retenção explícita, e consentimento separado para qualquer provedor remoto.

## 5. Tradução proposta para o Sieghart nativo

| Papel atual | Uso plausível dos padrões | Fronteira a manter |
| --- | --- | --- |
| **Sig** | Coordenar pedido e escolher um executor por tarefa; mostrar estado real no Agent Workspace. | A seleção por Sig é uma proposta; o app hoje apresenta Sig como personagem, sem runtime de agentes. |
| **Toni** | Ferramentas tipadas de arquivos e comunicação com prévia/resultado. | Só operar recursos autorizados pelo usuário; preservar confirmação de arquivos já existente. |
| **Ada** | Tarefas de código/GitHub após autorização de repositório e escopo. | O “Coding Specialist” adicional do adendo precisa ser definido como subpapel ou especialização, sem duplicar Ada por padrão. |
| **Gantt** | Calendário e tarefas agendadas finitas. | Não converter alerta local em agente autônomo permanente. |
| **Rita** | Sugestões de pausa e saúde com dados mínimos. | Não inferir informações sensíveis de memória geral sem consentimento específico. |
| **Elinor** | Finanças e recursos com leitura autorizada e fonte/proveniência. | Alterações de orçamento pedem prévia e aprovação; transferências e investimentos ficam fora do escopo padrão. |

Estas associações são **propostas**; os papéis atuais estão definidos em [`CompanionAvatars.swift`](../../Sieghart/Shared/Components/Companion/CompanionAvatars.swift). O Agent Workspace proposto deve distinguir `queued`, `running`, `waitingForUser`, `completed`, `failed` e `cancelled`; exibir agente, fontes, ferramentas concedidas, passo, resultado e histórico mínimo. Contexto compartilhado só por referência consentida; memória privada por agente/tarefa quando necessária; delegação como nova tarefa com escopo reduzido e trilha de autoria. Nada disso está implementado neste lote. Veja a [comparação com a arquitetura atual](../comparisons/openjarvis-vs-sieghart-architecture.md) e a [comparação das opções A–E](agent-runtime-comparison.md).

## 6. Portões para uma futura prova de conceito

Antes de escolher serviço Python, runtime reutilizado ou implementação Swift, criar uma tarefa pequena que percorra pedido → ferramenta permitida → confirmação → resultado → cancelamento/reinício. Medir em hardware real inicialização, latência, RAM/CPU, energia em repouso e sob carga, comportamento offline e após suspensão. Testar especialmente: tentativa de ferramenta fora da allowlist; timeout durante ação mutável; retry após interrupção; exclusão de memória e traces; analytics desligado; serviço local autenticado. Esses são **testes futuros propostos**, não resultados desta pesquisa. Qualquer código ou teste no Sieghart deve ficar em worktree separado da árvore em desenvolvimento, com passos reproduzíveis para o usuário.

**Conclusão:** OpenJarvis oferece contratos e mecanismos concretos que ajudam a especificar uma camada de agentes nativa. A evidência atual sustenta referência arquitetural e protótipo seletivo; não sustenta incorporar todo o runtime nem prometer autonomia, concorrência, privacidade ou eficiência no macOS sem experimentos adicionais.
