# OpenJarvis × Sieghart — viabilidade de integração

**Data da análise:** 13 de outubro de 2026. **Código examinado:** [OpenJarvis no commit `108d257188cbad85f2e50209d9a61669ea4dec33`](https://github.com/open-jarvis/OpenJarvis/commit/108d257188cbad85f2e50209d9a61669ea4dec33). As conclusões sobre execução são de leitura do código e da documentação dessa revisão; nenhum instalador, DMG, modelo, servidor, ferramenta ou agente OpenJarvis foi executado neste Mac. A [versão desktop distribuída](https://github.com/open-jarvis/OpenJarvis/releases/tag/desktop-v1.0.2) foi publicada de outro commit, de modo que o comportamento do pacote distribuído não deve ser igualado automaticamente ao do `main` analisado.

## Decisão para o estado atual do Sieghart

**Proposta:** usar OpenJarvis como **referência arquitetural (A)**, preservando interface, permissões, ciclo de vida e serviços do Sieghart em Swift/SwiftUI. A arquitetura híbrida **(E)** fica como possibilidade condicionada a uma prova de conceito isolada para alguma capacidade que o runtime nativo não ofereça com custo aceitável. Não incorporar o projeto como dependência agora.

Essa decisão não desvaloriza o projeto. OpenJarvis fornece abstrações de agente, ferramentas, memória, agendamento e inferência local. Entretanto, seu caminho principal é Python com extensão Rust e processos auxiliares; a aplicação desktop própria usa Tauri e inicia `jarvis serve` e Ollama. Para o Sieghart, isso implica distribuição, atualização, autorização e consumo de recursos adicionais que ainda não foram medidos. [Dependências e extras](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/pyproject.toml#L1-L77), [gerência de processos no desktop](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src-tauri/src/lib.rs#L378-L461).

## A–E: alternativas pedidas no adendo

As classificações abaixo são **avaliação arquitetural**, não medições em Apple Silicon.

| Alternativa | Integração com macOS e Swift | CPU, memória, bateria e manutenção | Segurança, extensibilidade e licença | Juízo atual |
| --- | --- | --- | --- | --- |
| **A. Referência arquitetural** | Contratos de agentes, ferramentas, memória e agendamento inspiram protocolos Swift; integração 100% nativa | Nenhum processo OpenJarvis acrescentado; exige implementar e manter os contratos escolhidos | Permissões e persistência ficam sob controle do Sieghart; estudar ideias não requer incorporar código | **Recomendada agora** |
| **B. Runtime local reutilizável** | Chamar API/CLI Python a partir de Swift exige empacotamento, IPC, versão e supervisão próprios | Python, extensão Rust, backend de inferência e modelos podem competir com a UI nativa; custo não medido | Ferramentas e MCP são extensíveis, mas a configuração padrão não é uma fronteira de autorização por agente; Apache 2.0 para o código do repositório | Não adotar sem prova de conceito |
| **C. Serviço separado controlado por Swift** | Serviço isolado com API local é tecnicamente plausível; o próprio desktop do projeto inicia `jarvis serve` | Maior isolamento de falhas e processo encerrável, com custo de inicialização, memória residente e atualizações | Precisa de autenticação local, lista explícita de ferramentas, aprovações no host e política de dados; não confiar apenas no loopback | Melhor formato **se** algum dia reutilizar o runtime |
| **D. Base de uma implementação Swift nativa** | Portar agentes/contratos conceituais para Swift preserva a experiência nativa; não existe biblioteca Swift pronta para anexar ao Sieghart | Sem runtime Python no produto, mas grande esforço de reimplementação e risco de divergência do upstream | Controle fino das APIs Apple e permissões; eventual tradução de código exige revisão da licença e das dependências | Usar conceitos via A, sem port integral |
| **E. Híbrida** | Núcleo Swift com adaptador opcional para um serviço OpenJarvis ou MCP | Pode manter ocioso o serviço opcional; requer medir arranque, repouso, carga e suspensão | Especialistas continuam subordinados ao autorizador do Sieghart; serviço externo recebe apenas tarefas e dados delimitados | **Candidata futura**, sujeita a testes |

**Base das avaliações:** o instalador de código fonte configura `uv`, ambiente Python, Ollama, modelo inicial e uma extensão Rust em segundo plano; macOS Intel e Apple Silicon são declarados suportados. `jarvis gui` requer Node.js 22+ em checkout de fonte. O pacote Tauri possui permissões de executar processos e, no entitlements macOS da revisão, declara app sandbox desativado. Isso descreve OpenJarvis, não uma exigência para a arquitetura proposta de Sieghart. [Instalação](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/getting-started/install.md#L1-L64), [notas macOS](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/getting-started/macos.md), [Tauri](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src-tauri/tauri.conf.json), [entitlements](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src-tauri/Entitlements.plist), [capacidades da janela](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src-tauri/capabilities/default.json).

## Interface técnica possível para C/E — proposta, não implementação

```text
Agent Workspace (SwiftUI)
  → Sieghart Orchestration Layer (Swift): identidade, delegação e estado
  → Authorizer (Swift): escopo por tarefa, consentimento e auditoria
  → adaptador opcional IPC/HTTP local
  → processo OpenJarvis separado, com modelo e ferramentas aprovados
```

O adaptador deveria transmitir um pedido limitado, ID da tarefa, agente responsável, prazo e **apenas** os dados necessários. O Sieghart conservaria a decisão de autorizar cada ação externa. Respostas de ferramentas seriam tratadas como dados não confiáveis antes de alterar arquivos, agenda ou outros recursos. Cancelamento e encerramento do processo deveriam acompanhar o estado do trabalho na UI. Essa divisão é uma **proposta para avaliação**, não um contrato já fornecido pelo OpenJarvis.

O serviço HTTP de OpenJarvis usa `127.0.0.1:8000` por padrão; sua rotina de inicialização recusa bind fora de loopback sem chave de API. Para uma integração real, **proposta:** porta dedicada/efêmera ou canal de IPC com credencial por sessão, autenticação inclusive no loopback, processo sob conta de menor privilégio possível, término após inatividade e nenhuma exposição direta de endpoints de administração à UI. O endpoint HTTP existente e o `MCPServer` não são, por si, um mecanismo de permissão do macOS. [Configuração de servidor](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1161-L1186), [middleware e bind seguro](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/server/auth_middleware.py#L30-L124), [servidor MCP](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/mcp/server.py#L43-L83).

## Permissões e execução de ferramentas

**Verificado no código:** `tools.enabled` e `agent.tools` começam vazios. A ausência de ferramentas embutidas reduz a superfície inicial, mas a presença de classes de segurança não equivale a autorização por agente: `SecurityConfig.enabled` nasce `true`, enquanto `CapabilitiesConfig.enabled` e `default_deny` nascem `false`. Os perfis `shared` e `server` ativam RBAC com `default_deny=true`; o perfil pessoal não o faz automaticamente. Uma política explícita por identidade deve definir quais operações cada especialista pode realizar. [Configuração de agentes/ferramentas](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1120-L1148), [configuração de segurança](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1420-L1498), [guia de capacidades](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/security.md#L62-L109).

Há duas nuances especialmente relevantes para Sieghart:

1. `shell_exec` executa comandos como o usuário do processo, sem lista de comandos permitidos e sem sandbox ativado por padrão. O `code_interpreter` atual valida a AST e restringe o subprocesso, mas o próprio código recomenda Docker ou desligamento para código não confiável; o sandbox de contêiner está desligado por padrão. A política de nomes sensíveis das ferramentas de arquivo não protege contra leitura via shell. [Guia de acesso ao sistema](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/system-access.md#L1-L73), [shell](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/tools/shell_exec.py#L51-L98), [interpretador](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/tools/code_interpreter.py#L1-L16), [sandbox default](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1549-L1558).
2. A marca `requires_confirmation` não garante diálogo humano. O dispatcher pergunta somente quando recebe callback interativo; `jarvis ask` fornece callback que aprova, e a documentação informa aprovação automática no servidor/desktop. O campo `security.enforce_tool_confirmation` é aceito na configuração, mas o guia oficial diz que não é aplicado nesse fluxo. Aprovações de Sieghart precisam existir **antes** de uma chamada autorizada ao backend. [Dispatcher](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/tools/_stubs.py#L400-L418), [CLI `ask`](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/cli/ask.py), [guia de confirmações](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/system-access.md#L75-L105).

**MCP exige seleção explícita.** O loader aceita servidores HTTP ou subprocessos stdio e filtros `include_tools`/`exclude_tools`. Porém, quando servidores externos estão configurados e a lista geral de ferramentas está vazia, `SystemBuilder._resolve_tools` adiciona todas as ferramentas descobertas desses servidores. O `MCPServer` interno também pode descobrir ferramentas embutidas amplas quando exposto sem uma lista recebida. **Proposta:** permitir somente ferramentas nomeadas por tarefa e autenticar cada chamada no autorizador do Sieghart; não tratar descoberta como concessão. [Guia MCP](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/mcp-external-servers.md#L1-L75), [seleção no builder](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/system/builder.py#L464-L533), [autodescoberta MCP](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/mcp/server.py#L87-L210).

No macOS, acesso a dados protegidos por TCC depende do processo que hospeda o backend. Full Disk Access, Automação e outras autorizações não podem ser inferidas de uma chave TOML. Um serviço OpenJarvis separado receberia sua própria identidade/processo para revisão de permissões; não conceder Full Disk Access como atalho de integração. [Guia oficial de acesso no macOS](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/system-access.md#L107-L155).

## Dados locais, análises externas e retenção

**Verificado:** OpenJarvis guarda configuração, credenciais, bancos, caches, logs, skills e outros estados sob `~/.openjarvis` por padrão, com opção `OPENJARVIS_HOME`. Métricas de inferência e traces usam SQLite. O registro de auditoria de segurança é append-only e a documentação não descreve rotação automática. Para um eventual serviço, **proposta:** diretório próprio de dados por perfil do Sieghart, chaves fora dos prompts e traces, prazos de retenção definidos pelo usuário, exclusão verificável e desligamento independente para histórico/telemetria. [Raiz de dados](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/getting-started/configuration.md#L8-L55), [telemetria e traces](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/telemetry.md#L1-L15), [auditoria](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/architecture/security.md#L132-L155).

**Privacidade que precisa de decisão explícita:** além das métricas SQLite locais, existe análise de uso externa por PostHog. `AnalyticsConfig.enabled` nasce `true` e o cliente Python prepara envios de eventos de uso com um UUID persistente, após filtragem de propriedades. O instalador de código fonte também constrói beacons de estágio de instalação. O código frontend só inicia o SDK se o endpoint de identidade informar `enabled=true`; suas chamadas `track()` passam propriedades diretamente ao PostHog, sem a mesma função Python de redação. Isso não prova que conteúdo pessoal tenha sido transmitido em uma execução real, pois não houve captura de rede nem auditoria de todos os chamadores; prova que a proteção do backend não cobre automaticamente o frontend. [Configuração externa](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/core/config.py#L1210-L1228), [cliente Python](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/analytics/client.py#L31-L103), [instalador](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/scripts/install/install.sh#L239-L359), [cliente frontend](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/frontend/src/lib/analytics.ts#L66-L145).

Há uma **divergência verificável**: o `CHANGELOG` declara que `DO_NOT_TRACK` e `OPENJARVIS_NO_ANALYTICS` desativam analytics, inclusive no instalador. No commit analisado, `is_analytics_enabled()` apenas retorna `cfg.enabled`, e a função `analytics_enabled()` do instalador sempre retorna sucesso. Portanto, **não assumir** que essas variáveis interrompem o envio nessa revisão. `[analytics] enabled = false` é lido pelo backend e impede a criação do cliente; o instalador tem caminho de beacon próprio, anterior a essa configuração. A documentação também mistura alegações de PostHog hospedado pela equipe e PostHog Cloud, então a localização real dos dados não foi confirmada. [Alegação do histórico](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/CHANGELOG.md#L219-L225), [função atual](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/analytics/identity.py#L47-L50), [função do instalador](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/scripts/install/install.sh#L246-L255), [inicialização do servidor](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/src/openjarvis/server/app.py#L440-L480), [documento de analytics](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/telemetry.md#L1-L17).

O comando `jarvis scan --data-boundaries` verifica a **configuração** e os tipos de armazenamento encontrados; não intercepta tráfego nem prova que determinada informação saiu do computador. O modo `--strict` acusa avisos como analytics e bind amplo. Esse diagnóstico serviria como uma checagem de preparação de uma prova de conceito, junto com inspeção de tráfego e dos arquivos realmente gravados. [Escopo do diagnóstico](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/user-guide/data-boundary-scan.md#L1-L76).

## Condições para reavaliar C/E

Antes de decidir por um serviço opcional, uma prova de conceito em **worktree próprio do Sieghart** deveria demonstrar: tarefa finita e cancelável; reinício após falha; controle de ferramentas por agente; aprovação real de operações; nenhuma transmissão externa não autorizada; armazenamento com exclusão; e medição no Mac de destino de tempo de arranque, CPU, memória, energia/bateria em repouso e sob carga, temperatura e comportamento após suspensão. Comparar as mesmas tarefas com o caminho nativo Swift/Apple Intelligence/Ollama escolhido pelo produto. O projeto suporta Apple Silicon e oferece integração MLX opcional; a integração com Apple Foundation Models em seu pacote exige condições adicionais, como macOS 26+, Apple Intelligence e Xcode completo. **Nenhum número de desempenho ou autonomia de bateria foi verificado aqui.** [Notas macOS](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/docs/getting-started/macos.md), [extras MLX/AFM](https://github.com/open-jarvis/OpenJarvis/blob/108d257188cbad85f2e50209d9a61669ea4dec33/pyproject.toml#L48-L111).

Esta pesquisa não implementou nem testou funcionalidade no Sieghart; portanto, não há passos de teste de produto a executar agora. A definição de uma experiência com OpenJarvis deverá incluir instruções reproduzíveis para instalação isolada, cenários, métricas e reversão antes de qualquer integração ao aplicativo principal.
